# 后台反馈问题分析

更新时间：2026-06-10

数据来源：当前项目数据库 `prisma/dev.db` 的 `Feedback` 表，只读查询。当前共有 16 条反馈，其中 12 条 `new`，4 条 `archived`。

## 一句话结论

这批反馈表面上是按钮、颜色、图集、账号显示等零散问题，本质上是在暴露 SD2 从“单人生成工具”走向“多人、多项目、多来源、可审计生产系统”时的底层能力缺口。

核心问题不是“页面不好看”，而是：

- 权限边界要可验证。
- 生成流程要能连续生产。
- 用户偏好和素材资产要能沉淀。
- 产出要能看清归属、来源和付款主体。
- 状态和颜色语义不能误导用户。

## 第一性原理拆解

### 1. 系统最终要保障什么

从用户和管理者角度，SD2 必须保障五件事：

- 我只看到我应该看到的任务和产出。
- 我可以连续生成多段内容，不被上一条任务状态卡住。
- 我用过的模式、参数、参考图、图集可以复用和管理。
- 每条产出都能明确知道是谁生成、属于哪个项目、由谁付费。
- 页面状态、颜色和文案表达的是正确语义。

### 2. 当前反馈暴露的真实问题

这批反馈可以分为六类：

- 权限与数据隔离。
- 项目级计费与额度。
- 连续生成工作流。
- 图集和参考素材管理。
- 产出归属与身份展示。
- 状态语义和基础交互体验。

## 问题分组与优先级

### P0 - 权限与计费边界

#### 问题 1：普通用户是否能看到其他人的任务和产出

原始反馈：

> 查一下每个角色里看我的任务是否会看到其他人的产出内容，按道理只有管理员可以看到所有人

本质：

这是数据隔离和权限矩阵问题，不是普通 UI bug。如果普通用户、项目成员或外部用户能看到不该看的任务，这是安全问题。

需要验证的边界：

- 普通用户只能看到自己的任务，或自己有权限访问项目内的任务。
- 项目成员只能看到所在项目允许访问的任务。
- 项目管理员能看到自己管理项目内的任务，但不等于能看全站。
- 系统管理员才能看全站产出。
- `/tasks`、`/tasks/:id`、`/api/video/list`、`/api/video/status/:id`、`/api/video/thumbnail/:id`、`/admin/outputs` 的权限判断必须一致。

风险：

- 如果只改前端隐藏按钮，API 仍可能泄露数据。
- 如果后台产出和普通任务页权限不一致，会出现“页面看不到但接口能拿到”的问题。

建议处理：

- 先做只读权限审计，再决定是否修复。
- 用不同角色账号验证任务列表、详情页、视频预览、截图接口和后台输出接口。
- 这项应作为 P0 单独闭环。

#### 问题 2：项目代付和项目额度

原始反馈：

> 把项目设置成一个只要在这个管理员指定的项目里，就能自动扣除点数，相当于项目帮用户付费；每个项目管理员都可以独立设置额度

本质：

这是计费主体从用户扩展到项目，不是加一个开关。它会影响点数冻结、扣费、退款、额度、项目权限和成本审计。

必须先回答的问题：

- 项目额度从哪里来，是项目账户独立余额，还是管理员给项目配置每日/月度额度？
- 谁能开启项目代付，是系统管理员，还是项目管理员？
- 项目成员生成时，优先扣用户点数还是项目额度？
- 项目额度不足时，是禁止生成、回退用户点数，还是走审批？
- 外部 API 传入 `project_id` 时，是否允许使用项目代付？
- 成本账中如何记录 `billing_scope=user|project`、`billing_account_id` 和操作者？
- 项目管理员能不能看到成员的消耗明细？

风险：

- 直接改扣费逻辑可能造成重复扣费、绕过个人额度、退款错账。
- 外部 API 和站内生成如果走不同扣费规则，会导致账本不可审计。

建议处理：

- 单独写 Spec，不和 UI 修复混在一起。
- 先设计数据模型和账本规则，再做接口与页面。
- 需要覆盖创建、冻结、成功扣除、失败退款、成本导出和管理员审计。

## P1 - 连续生成与生产效率

#### 问题 3：任务创建成功后，提示不应阻塞下一次生成

原始反馈：

> 如果已经创建成功，进入排队，那任务已创建的提示应该消失，可以创建下一段

本质：

生成器应该是连续生产工具。创建成功后，当前任务进入后台队列，表单应恢复为可编辑状态，用户可以继续创建下一段。

需要明确的交互：

- 创建成功后是否保留上一次 prompt。
- 是否自动清空 prompt。
- 是否保留参考图和参数。
- 成功提示显示多久。
- 新任务队列入口放在哪里，避免用户不知道上一条任务在哪看。

建议处理：

- 创建成功后把任务写入队列/任务列表提示。
- 表单恢复可提交状态。
- 成功提示用非阻塞 toast 或队列提示，不长期占住表单。

#### 问题 4：保存每个人最后一次生成设置

原始反馈：

> 每个人用的生成模式，要默认保存最后一次生成的设置

本质：

这是用户偏好持久化。用户每天重复生成时，不应该每次重新选模式、比例、时长、分辨率等参数。

建议保存的字段：

- `generation_mode`
- `ratio`
- `duration`
- `resolution`
- `generate_audio`
- `watermark`
- `return_last_frame`
- 最近使用的项目或工作台上下文是否也要保存，需要单独确认。

风险：

- 不应把一次性素材、临时 URL、外部签名地址保存为长期偏好。
- 多设备登录时，要决定偏好是本地存储还是服务端按用户保存。

建议处理：

- 如果只解决当前浏览器体验，可先用 localStorage。
- 如果要跨设备一致，建议服务端加用户偏好配置。

#### 问题 5：返回按钮应回到来源页

原始反馈：

> 返回任务这个按键，改成哪里来的回哪里去

本质：

任务详情页有多个入口：任务列表、生成页、项目页、后台产出、外部链接。硬编码返回 `/tasks` 会破坏导航上下文。

建议处理：

- 优先使用显式 `return_to` 参数。
- 没有 `return_to` 时再 fallback 到 `/tasks`。
- 不建议只依赖浏览器 history，因为用户可能直接打开任务链接。

## P1 - 素材和图集资产管理

#### 问题 6：图集缺少封面/截图

原始反馈：

> 参考图集的图集卡片需要有截图

本质：

图集卡片现在缺少可识别线索。用户管理多个图集时，只看名称不够，应该展示封面或最近图片缩略图。

建议处理：

- 图集卡片显示封面图。
- 默认封面可取第一张参考图。
- 后续可支持手动设置封面。

#### 问题 7：图集缺少删除按钮

原始反馈：

> 图集没有删除按键

本质：

图集已经是资产库的一部分，需要生命周期管理。没有删除/归档会导致素材越积越多。

需要确认：

- 删除是软删除还是硬删除。
- 删除图集是否删除图集内图片。
- 已经被历史任务引用的参考图是否保留。
- 谁有权删除共享图集。

建议处理：

- 默认做软删除或归档。
- 历史任务引用的素材不能被破坏。
- 删除前提示影响范围。

#### 问题 8：图集缺少重命名、新建入口和相关管理动作

原始反馈：

> 已保存的，图集名字修改，没有做这个功能和按钮，新建图集按钮删除

本质：

图集不是单纯展示列表，而是素材管理对象，至少需要基础 CRUD。

建议补齐：

- 新建图集入口。
- 重命名图集。
- 删除/归档图集。
- 图集卡片封面。
- 权限控制和空状态。

## P1 - 产出归属和身份展示

#### 问题 9：产出列表和视频详情要显示生成者与头像

原始反馈：

> 在产出留存队列里，所有的项目都应该显示生成者和生成者的头像，包括在打开具体视频的时候，视频上方也应该有显示

本质：

多人协作下，每条产出必须能看清归属。尤其外部 API、项目代付、后台审计同时存在时，产出只显示视频不够。

建议展示：

- 生成者头像。
- 生成者名称。
- 所属项目。
- 来源类型，例如 Web、Codex API、外部系统名称。
- 任务创建时间。

风险：

- 不同页面显示的“生成者”口径要一致，避免有的用 `user_id`，有的用 `owner_user_id`。
- 外部 API 任务绑定用户和实际外部调用者可能不同，需要展示来源字段辅助判断。

#### 问题 10：账号信息后缀太长，身份展示不友好

原始反馈：

> 为什么我的这个账号的信息后缀这么长，别人都是邮箱？帮我改改显示

本质：

系统把技术标识当成用户可读身份展示了。Feishu `open_id` 或本地 fallback 邮箱不适合作为主展示名。

建议展示优先级：

- 用户姓名。
- 企业邮箱或真实邮箱。
- 手机号或短用户名。
- 技术 ID 只在管理员详情页或调试信息里展示。

风险：

- 不要直接覆盖原始身份字段，避免影响 Feishu 绑定。
- 应新增展示格式化逻辑，而不是删除 open_id。

## P2 - 状态语义和视觉反馈

#### 问题 11：“请写提示词”不应使用红色

原始反馈：

> 请写提示词这几个字，也不要用红色，蓝色即可

本质：

红色在产品里应表示错误、危险或阻断。输入引导不应使用错误色，否则用户会误以为系统报错。

建议处理：

- 空 prompt 引导使用中性或品牌蓝。
- 真正提交时报错才用红色。

#### 问题 12：“提交中”不应使用红色

原始反馈：

> 提交中不应该是个红色，用绿色即可

本质：

提交中是进行态，不是错误态。红色会传达失败或危险。

建议处理：

- `submitting/running/queued` 使用绿色、蓝色或中性色。
- `failed/error/danger` 才使用红色。
- 全站状态颜色应统一。

## 推荐处理顺序

### 第一批：先保安全和账本

1. 权限审计：验证普通用户、项目成员、项目管理员、系统管理员在任务列表、详情、视频状态、截图、后台产出中的可见范围。
2. 项目代付先写 Spec，不直接实现。明确额度来源、扣费优先级、冻结/退款规则、账本字段、后台审计和外部 API 归属。

### 第二批：提升连续生成效率

1. 创建成功后释放生成表单，不让成功提示阻塞下一次提交。
2. 保存用户最后一次生成参数。
3. 任务详情返回支持来源页。

### 第三批：补齐素材资产库

1. 图集卡片封面。
2. 图集重命名。
3. 图集删除/归档。
4. 新建图集入口和空状态。

### 第四批：补齐多人协作识别

1. 产出列表显示生成者头像和名称。
2. 视频详情页顶部显示生成者、项目、来源。
3. 账号展示逻辑优化，隐藏技术 ID。

### 第五批：修状态颜色和文案

1. “请写提示词”改为非错误色。
2. “提交中”改为进行态颜色。
3. 全站统一状态颜色语义。

## 不建议混在一起做的事项

- 项目代付不要和普通 UI 修复放在同一个变更里。
- 权限修复不要只改前端，要同时验证 API。
- 图集删除不要硬删除历史任务引用的素材。
- 身份展示优化不要破坏 Feishu 绑定字段。
- 状态颜色不要单点覆盖，应统一语义。

## 验收建议

- 权限类：用至少四类角色账号分别打开 `/tasks`、`/tasks/:id`、`/api/video/list`、`/api/video/status/:id`、`/api/video/thumbnail/:id`、`/admin/outputs`。
- 计费类：用一条成功任务和一条失败任务验证冻结、扣费、退款、成本导出。
- 生成流：连续创建两条任务，确认第一条进入队列后第二条可以继续提交。
- 图集类：创建、重命名、删除/归档、封面展示都要验证历史任务不受影响。
- 归属展示：Web 任务和 Codex API 任务都要能显示生成者、项目和来源。
- 状态颜色：提交中、排队中、成功、失败、输入引导必须有一致颜色语义。
