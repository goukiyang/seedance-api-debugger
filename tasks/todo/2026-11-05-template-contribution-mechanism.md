## 2. 方案比较与选择

| 方案 | 作用与代价 | 结论 |
| --- | --- | --- |
| A：他人首次成功复用自动奖20点 | 反馈快，但一次调用若扣5点，作者得20点；两人各互用一次，合计消耗10点、获奖40点，净增加30点。模板来源去重只能限制次数，不能证明真实有用。 | 不推荐直接启用；保留为风险对照。 |
| B：首次复用自动奖2点 | 降低常见低价调用的净收益，但免费或更低价路径仍可能赚点，且小额可能缺乏激励。 | 不是单靠调小数字就解决防刷。 |
| C：复用自动记贡献，真实业务采纳经独立核准后奖200点 | 贡献反馈与资金发放分开，低成本调用本身不自动生钱；需要负责人提供业务依据、管理员合并核准，有审核负担，误批仍会误奖。 | 推荐首轮试行；不是已经获批的配置。 |

选择C：前台只有现有可用点数，不创建第二种可兑换货币。贡献显示“帮助多少位同事、哪些模板被采纳”，不是待兑换余额。不按模型消费金额比例发奖，避免鼓励使用更贵模型。

## 3. 建议参数及边界

| 参数 | v1建议值 |
| --- | --- |
| 活动周期 | 14天；明确起止时刻，记录统一时区，页面按用户时区展示 |
| 全站活动预算 | 20,000点，默认未批准、未拨付、未启用 |
| 自动复用奖 | 0点，仅记录贡献；旧草案20点不默认采用 |
| 每笔项目采纳奖 | 200点，整笔核准，不把不足额度拆成小奖 |
| 个人本轮上限 | 2,000点，即最多10笔采纳奖 |
| 同一模板来源本轮上限 | 1,000点，即最多5个不同合格项目 |
| 同一业务项目本轮上限 | 600点，即最多3个不同合格模板 |
| 再次计奖 | 同一真实项目+同一模板来源，已有奖励后不因新版本、换活动或换作者再奖 |
| 发布、点赞、收藏、回复、自用 | 不直接给可消费点数；优质提问和帮助可留非金钱贡献记录 |

当前口径1元=100点：20,000点仅为200元名义站内额度，不是已发生供应商实扣，也不保证全部未来API费用恰好200元。活动奖励预算与正常生成预算分开控制。

资金来自平台批准的内部奖励额度，不向模板使用者额外收费、不自动扣其个人或项目预算。奖励进入已有长期点数余额，沿原消费规则使用，不另设兑换币、转账或提现。基础工作额度与奖励分开，不发布模板也不因此降低原有工作配额。

## 4. 谁、什么内容、什么任务可参加

1. 仅有效内部账号。第一批采用真实业务项目ID、合格模板来源ID的明确参与名单；个人默认项目、测试项目、新建或改名项目不会自动入选。
2. 模板有用途、适用输入、可查看的效果样例和已知限制，引用素材允许共享及用于生成。普通发布和使用不因奖励审核受阻，也不要求全公司公开。
3. 首版每个参与模板登记一个受奖作者；共同作者保留署名，不做多级分成。官方系统模板不默认给管理员个人领奖。
4. 至少有一位作者之外的同事实际复用；原任务成功交付且对应站内结算明确。个人余额、周期配额、项目预算均可，是否花个人点数不作为价值判断。
5. 一个操作只认服务端冻结的一个主模板。纯手动复制、缺来源的历史记录、附属风格组和素材不猜归属，也不分别分账。
6. 一批多张或多视频最多记一次贡献；部分成功只认已实际交付且已明确结算部分。失败、取消和调试不计有效贡献；未知只核原任务，不凭超时认失败或自动重发。
7. 先显示提交/完成记录，真实业务采用必须另有证据；自动归入项目、下载或收藏不等于业务采纳。
8. 活动前的旧任务不追溯补奖。规则版本、参与状态、模板来源、模板版本和受奖作者按任务受理时事实记录；后续当前模板定义不能改写它们。

## 5. 采纳确认和资金承诺

正常路径：同事复用 -> 系统记录贡献 -> 负责人确认业务采用 -> 管理员核准且预留预算 -> 待到账 -> 原账户入账与可查询流水。

- 项目负责人对自己有权查看的实际产出确认“用于什么交付、解决了什么问题”，关联原任务及结果，不另填大份申请表。作者无需为每次普通使用手动申请积分。
- 管理员按项目/作者合并查看候选、确认金额及资金。受奖人不得终审自己的奖励；没有独立且获授权的审批人时暂缓该笔，不临时扩大任何人的权限。
- “待核准贡献”只显示数量和原因，不显示为已赚点数；未核准不承诺付款、不占用可用余额。
- 只有资格核准和预算预留均成功，才显示“200点待到账”。全站、作者、模板来源和项目限额都计算已发放+已预留，不能只看已到账。
- 额度不足整笔不核准，说明命中哪个上限，不暗中均摊或缩水、不挪用项目生成预算。预算不足不影响正常工作任务。
- 已预留的承诺在活动暂停或结束后继续兑现；活动暂停停止新的核准，未核准贡献不是已承诺奖励。现有候选按原事实保留，不能把活动结束解释成原任务失败。
- 正常已核准奖励以次日到账为运营目标；账号异常、原号核对或服务故障显示具体状态，不能用固定超时改成已到账。收到不确定回执只查原操作，不换号重发。

## 6. 原账、归属和退出保护

- 后续实现必须沿原账户和精度助手写入；奖励事实唯一、核准/预留、余额及关联流水的持久状态应有同事务归属，不能靠页面计数或先加余额后补流水。
- 同一操作号重放返回原回执，篡改原内容拒绝；不同操作号重复申领同一项目+模板来源也不再发。活动ID和模板版本不是重置终身唯一资格的办法。
- 模板复制/改名/另存保留来源族；真正的新模板须重新确认独立价值，语义相似不能假装已被简单哈希算法准确识别。
- 受奖人、规则及金额冻结在原奖励记录；转移维护人只影响之后的新任务，原奖励不自动转给接手人。撤回停止新任务参加，原合法受理事实保留；侵权/作弊另行暂停核对。
- 作者禁用或离职时暂停尚未入账部分，保原承诺和记录，管理员核实处理；不把钱发到别的账户，也不销毁历史。
- 作者只能看奖励摘要和被允许的凭证，不因领奖取得他人私有任务、提示词、原图或项目权限。
- 纠错另记关联原流水的冲正，不删除、改写旧账。重复冲正不重复扣；余额已用完时不自动扣成负数，差额及处理决定仍留记录，不能冒称已经追回。
- 冲正不自动重开本轮资格或奖励名额；预留尚未支付的撤销可以有原因地释放额度，但原取消回执保留，普通重试不能绕过取消重新领。
- 贡献奖励是内部额度分配，不当作供应商实际API支出再次加进原项目成本。真实成本仍按各原生成任务及供应商账单记录，未知保持未知。

## 7. 防刷、合作和可用性

正常互相帮助不等于作弊，共用办公IP不是拒奖证据。重点核对重复包装、无真实业务采用、伪造结果、关联账号和审批人与受奖人重合。管理员只拿到一个“已批准”布尔值不等于证据已核验，离线模型不会识别真实谎报。

首轮用有限参与名单、可访问的结果凭证、独立核准、统一限额和抽查限制风险，不新建复杂风控平台。审核失误仍可能造成误发，预算只能限制名义奖励量；实际API调用成本另有原预算，不能声称总损失只剩200元。

普通反馈和低评分不扣作者奖励。奖励异议关联具体记录，责任管理员给出保留、补发、调整或继续核对的原因，受奖人不能自批。处理时长应实测；100笔若每笔核对1分钟就是100分钟，不能假定批量按钮意味着零审核成本。

用户入口建议：模板卡说明参与状态/适用场景/默认规格参考费用；作品旁直接用模板和就地提问，保当前主图、草稿和报价确认；本人贡献页显示有效复用人数、采纳项目数、已核准待到账/已到账；原流水显示奖励来源。正常生成无需先评价或申请奖励。上述均为交互设计，尚未实现或浏览器验收。

试行判断不只看复用次数：对照试行前同长度窗口，分别记录贡献作者数、真实使用同事数、被业务采纳的模板数、重复复用情况，以及每笔采纳奖励的审核时间和申诉原因。样本小或缺基线时只报观察、不宣称提升；不按API花费或公开个人消费榜评价贡献。若核准太慢或规则看不懂，先调整流程，不直接提高奖额刺激调用。
