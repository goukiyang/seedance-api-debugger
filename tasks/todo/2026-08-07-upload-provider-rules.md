# 上传限制分层与生成准入收口

## 1. 大白话目标复述

这次要解决的是：不要再把“上传限制”和“生成限制”混在一起。用户上传素材时，系统只拦已经明确不能保存、明显超过基础能力或已经确认会失败的问题；如果只是“不确定能不能用于当前模型生成”，先允许进素材库，再在生成前做清楚、可解释的检查。

做到完成的标准是：同一个文件在生成页、资产页、上传历史、图集和模板里走同一套上传入口；上传成功只代表“素材已入库”，生成前再判断“这个素材能不能给当前 Seedance 2.0 生成用”。未知问题不提前硬拦，Provider 真实返回后记录错误码、素材摘要和规则缺口，后续再补规则。

本轮收口原则：不重写上传平台，不引入新依赖，不把所有官方规则一次性做成复杂配置系统；先把当前已知限制做成一张可维护规则表，并把误伤用户的限制从上传阶段挪到生成阶段。

## 2. 具体可执行任务

- [ ] T1. 建立“限制来源表”，先把规则说清楚
  - 修改对象：`src/lib/provider/reference-media-policy.ts`，必要时新增 `src/lib/provider/seedance-media-rules.ts`。
  - 执行内容：把限制分成四类：`官方明确要求`、`历史失败确认`、`内部链路限制`、`待确认不硬拦`。
  - 首批写入：图片/视频/音频大小、数量、音频不能单独用、公网 URL、最低像素、Seedance 2.0 视频/音频 2-15 秒、图片/视频宽高比、视频 FPS、视频总时长、Provider asset Active。
  - 完成标准：代码里能直接看出每条限制属于上传入库、生成前拦截、还是仅记录观察；不再靠散落常量猜规则来源。

- [ ] T2. 放宽素材库上传，只做基础入库限制
  - 修改对象：`src/lib/assets/site-upload.ts`、`src/app/api/assets/upload/route.ts`、`src/lib/assets/direct-upload.ts`、`src/lib/http/file-upload.ts`。
  - 执行内容：上传阶段保留文件大小、基础 MIME、文件体可读取、登录态和存储链路检查；把“当前模型生成才需要”的时长、FPS、宽高比等从上传阶段移出。
  - 特别处理：`ffprobe` / 浏览器 metadata 读不到视频或音频信息时，不直接说上传失败；允许素材入库但标记元数据缺失，生成前再尝试补探测或给出“暂不能确认能否生成”的提示。
  - 完成标准：小图片、小视频、小音频不会因为生成模型规则提前上传失败；上传失败文案只描述上传链路或文件本体问题。

- [ ] T3. 生成前统一准入检查，只拦已知必失败问题
  - 修改对象：`src/app/api/tasks/create/route.ts`、`src/components/GenerationComposer.tsx`、`src/components/ReferenceStrip.tsx`、`src/components/ErrorTranslator.tsx`。
  - 执行内容：生成前统一调用规则表，检查当前 Seedance 2.0 明确限制：图片最多 9 张、视频/音频最多 3 个、音频不能单独使用、视频/音频必须公网 URL、已知宽高低于 409600 像素、已知时长不在 2-15 秒、已知格式不适合生成。
  - 不硬拦项：元数据缺失、未确认的格式扩展、官方没要求但内部还没验证的策略；这些只提示风险并记录，不提前禁止。
  - 完成标准：前端和后端返回同一类错误码和中文解释；后端仍是最终兜底，不能只靠前端。

- [ ] T4. 把“官方没要求但代码已限制”的项降级为链路说明
  - 修改对象：`src/lib/http/file-upload.ts`、`src/app/api/assets/upload/route.ts`。
  - 执行内容：重新处理旧表单 8MB、视频不能普通上传回退、分块只给大视频、`ffprobe` 失败即拒绝、素材库阶段强卡 2-15 秒这些限制。
  - 处理口径：如果是链路能力限制，就提示“当前上传通道限制”；如果是生成限制，就移动到生成前；如果没确认，就不硬拦。
  - 完成标准：用户不会再看到“1.6MB 图片请压缩”这类错误归因；视频上传链路失败不会被包装成文件不合规。

- [ ] T5. Provider 新错误进入“后补规则”闭环
  - 修改对象：`src/lib/provider/error-message.ts`、`src/lib/video/task-finalizer.ts`、上传/生成日志相关 helper。
  - 执行内容：Provider 返回未知错误时，保留 `code/message` 结构化摘要，关联任务、素材类型、尺寸/时长/格式等安全元数据；不直接把未知错误变成永久规则。
  - 完成标准：后台能看到“这次是素材规则问题、上传链路问题、Provider 拒绝、还是平台异常”；后续补规则有证据来源。

- [ ] T6. 回归测试和真实入口验证
  - 修改对象：新增或更新 smoke 脚本，优先复用现有 `scripts/reference-media-chain-smoke.ts`、`scripts/direct-upload-r2-smoke.ts`。
  - 测试样本：1.6MB 普通图片、低分辨率图片、WebM 视频、MP4 视频、OGG 音频、MP3/WAV 音频、超长视频、元数据读取失败样本、重复素材。
  - 验证命令：`npm run lint`、`npx tsc --noEmit --pretty false`、相关 smoke、`git diff --check`。
  - 完成标准：上传入库和生成准入的测试分开；不能用“上传成功”证明“生成可用”，也不能用“生成限制”阻断素材入库。

- [ ] T7. 部署和线上闭环
  - 执行内容：实现完成后按 sd2 项目规则执行 `youdoo-sites build sd2`、`youdoo-sites restart sd2`，再从公网验证 `/api/config`、`/login` 和真实上传入口。
  - Git：聚焦提交，push 当前分支；必要时登记版本和回滚点。
  - 完成标准：明确区分本地已改、测试通过、Git 已推送、线上已加载、真实页面已验证。

## 3. 验收/审查内容

这些审查项需要创建独立子 agent 做只读审查；审查 agent 不改文件、不提交、不补实现，只判断是否达标、证据是否充分、风险是否遗漏，并输出“通过 / 不通过、证据、缺口、风险、下一步”。

- [ ] R1. 独立只读审查：限制分层是否清楚
  - 检查对象：规则表、上传入口、生成 API、前端提示。
  - 通过标准：每条限制能说明来源和生效阶段；没有把“生成不适合”提前变成“上传失败”。
  - 证据来源：代码 diff、规则表、错误码/文案检查。

- [ ] R2. 独立只读审查：是否只拦已知问题
  - 检查对象：`site-upload.ts`、`file-upload.ts`、`tasks/create/route.ts`。
  - 通过标准：官方没要求且我们没确认的问题不硬拦；已知必失败问题在生成前拦住。
  - 证据来源：源码、smoke 样本、Provider 官方限制对照。

- [ ] R3. 独立只读审查：未知错误是否进入后补规则闭环
  - 检查对象：Provider 错误处理、任务 finalizer、上传/生成日志。
  - 通过标准：未知错误保留结构化摘要，不再显示裸 HTML、`Unexpected token '<'` 或泛化“系统异常”；不会直接冻结成新规则。
  - 证据来源：模拟错误返回、日志摘要、用户文案。

- [ ] R4. 独立只读审查：真实入口是否一致
  - 检查对象：`/generate`、`/assets`、上传历史、图集、模板。
  - 通过标准：同一文件在不同入口上传入库口径一致；生成前限制口径一致；重复素材直接复用。
  - 证据来源：真实登录态页面检查、API 响应、Asset 记录。

- [ ] R5. 独立只读审查：部署闭环
  - 检查对象：构建产物、sd2 服务、公开 URL、Git 状态。
  - 通过标准：线上加载新构建；公网入口能看到新提示和新行为；Git 远端有可追踪版本。
  - 证据来源：`youdoo-sites status sd2`、公网接口、页面截图/DOM、`git status`、远端 commit。

## 4. 审查内容是否对齐目标

- [ ] A1. R1 是否对齐目标
  - 判断：审查项是否证明“上传入库”和“生成准入”已经分开。

- [ ] A2. R2 是否对齐目标
  - 判断：审查项是否能发现“官方没要求、我们没确认、但代码硬拦”的误伤项。

- [ ] A3. R3 是否对齐目标
  - 判断：审查项是否保证后续新问题可被记录、复盘和补规则，而不是继续靠猜。

- [ ] A4. R4 是否对齐目标
  - 判断：审查项是否覆盖真实用户入口，不只看单个 API 或单个页面。

- [ ] A5. R5 是否对齐目标
  - 判断：审查项是否证明线上可见，而不是只证明本地代码完成。

## 5. 停止条件

- 遇到需要打印 `.env`、R2 密钥、签名 URL、uploadToken、cookie、session 的情况立即停止，改用安全摘要。
- 需要真实付费生成时先停下确认；本任务默认只验证上传、准入和创建前错误处理。
- 如果修改会改变点数冻结/退款、Provider 计费或数据库迁移，先单独规划风险，不和本任务混做。
- 如果真实入口测试连续 3 次失败，不继续盲改；先列出现象、链路阶段和已验证证据，再决定下一步。
