## 1. 大白话目标复述

把当前“左侧拼图、右侧选帧工具”的两栏页面改成真正以拼图为主的全宽工作台：页面不显示左侧导航栏；“选帧、排版、查看原视频”放在拼图上方同一行；选帧时在上方展开一条全宽的内联工具区，不再占据右侧一大片空间。

逐帧操作不能再做到“每点一次就等服务端现拆一张原尺寸 PNG”。标准 3D 多视图短视频先一次性准备轻量预览帧，上一帧、下一帧、倍速步进、指定帧和滑轨都从已经准备好的预览里即时切换；只有用户点“使用这一帧”时才读取现有原尺寸 PNG，保证拼图、复制、下载和作品保存仍使用原画质。

本计划是在既有 D01–D20、MV05 和 R05 体验提案上继续收口，不删除已有的单格调帧、按住图片拖动换排列、命名、排版、复制、PNG/ZIP、作品保存、快速浏览、权限、恢复及未知请求保护。

## 2. 已核实的现状与根因

### 2.1 页面为什么浪费空间

- `src/app/multiview/page.tsx` 当前把拼图和工具区包在 `.workbench` 两列中；`src/app/multiview/multiview.module.css` 使用约 `2fr + 1fr`，右侧只放少量选帧/排版内容，工具区下方长期空白。
- “查看原视频”目前在页面最底部 `<details>`，选帧页签则在右栏。用户完成同一个任务需要上下、左右来回找。
- 全局壳层只对 `/tools/ultimate-canvas` 隐藏侧栏；`/multiview` 仍套用左侧导航，进一步压缩工作台。
- 用户截图清楚显示 8 张拼图已经需要横向空间，而右栏仍保留大面积空白。本轮截图已归档至第 10 节。

### 2.2 为什么“下一帧”会卡约一秒

已确认是本系统交互和提帧链路叠加，不是一个单独的按钮动画：

1. 前端在编辑帧变化后固定 `setTimeout(..., 180)`，先额外等待 180ms。
2. `loadFrame` 把所有帧请求串到同一个 `frameQueue`；当前帧还会再依次等待 `-1、+1、-2、+2` 邻帧。连续点击时，新目标会排在旧目标或旧预读后面，形成队头阻塞。
3. 每个未缓存帧都发一条 `cache: 'no-store'` 请求，完整下载原尺寸 PNG。
4. 服务端 `src/lib/video/multiview.ts` 每个缓存未命中帧都会单独启动一次 FFmpeg；命令先打开视频，再用 `select=eq(n\,frame)` 找帧，并压缩 PNG。没有常驻解码器，也没有轻量交互预览层。
5. 服务端只缓存最多 48 张／约 256MB 原尺寸 PNG；卡片、邻帧预读和快速点击会互相挤占。这个缓存适合最终导出画质，不适合作为唯一的交互预览来源。

本机对项目既有 4 秒、97 帧、640×640 样例做只读对照：当前等价“单次启动 FFmpeg 抽一张 PNG”首次约 0.47 秒；同机文件缓存热后约 0.07 秒；单次顺序生成全部 97 张、宽 320px 的轻量 JPEG 约 0.10 秒，总计约 1.2MB。终审又验证了 24 帧一组、6×4 的 JPEG 图集：共 5 个请求、约 0.95MB、生成约 0.39 秒，最后不足 24 帧的分组也能正确产出。图集比 97 个独立文件稍慢，但把请求数从 97 降为 5，且单块解码内存可明确封顶，因此本批固定采用有界图集而不是散图。以上只能证明“一次顺序准备”比“每点一次重启解码”更合理，不能冒充生产网络或最终 SLA；生产各阶段的精确占比仍需实施后用服务端计时确认。

## 3. 方案选择与开源核对

### 3.1 推荐方案：双层帧源

采用“轻量 JPEG 图集负责交互，原尺寸 PNG 负责最终使用”的双层方案：

- 工作台打开结果后由客户端显式请求预览 manifest；服务端在授权请求内用一次 FFmpeg 顺序解码准备 JPEG 图集，不依赖响应结束后的“后台继续跑”。图集协议 v1 固定每块最多 24 帧、6×4 排列、每帧长边不超过 320px；不足 24 帧的尾块记录真实帧数。
- 服务端派生缓存键使用任务/源对象、`sourceVersion`、协议与预览规格，不按账号重复存同一份文件；每次 manifest 和图集读取仍重新执行任务查看权限。浏览器缓存另按用户会话 epoch、任务、源版本和规格隔离，退出、换号、失权或换源立即释放 Object URL。
- 总帧数不超过 600 的标准短视频优先一次准备完整图集；更长来源只按当前目标准备有界分块并保留现有精确帧/原视频退化路线，不能承诺全片任意跳转都已预热，也禁止无上限生成全部预览。
- 前端只为当前任务维护有界预览缓存；逐帧、±10 帧、指定帧和拖动滑轨只切换已经准备好的预览，不再每次调用原尺寸提帧接口。
- 当前帧优先，旧目标请求可取消或结果作废；删除单一全局串行 `frameQueue`，邻帧预读不能挡住当前点击。
- 用户点“使用这一帧”时，服务端重新核对权限和 `sourceVersion`，再复用现有精确原尺寸 PNG 缓存／提取路径。原帧未就绪时只在应用按钮附近显示“正在准备原帧”，不阻止继续浏览预览。
- 拼图、复制、下载、ZIP、作品保存永远使用原尺寸帧；轻量预览不能进入最终产物，也不能扩大 view/use/download 权限。

### 3.2 为什么不直接换成浏览器解码库

| 方案 | 结论 | 原因 |
|---|---|---|
| 继续每帧启动 FFmpeg | 不采用 | 进程启动、从头解码、PNG 编码和网络请求会随点击重复，快速点击仍排队 |
| 原生 `<video>` seek + `requestVideoFrameCallback` | 只作可选即时反馈 | 可同步到实际呈现帧，但任意 seek 仍受关键帧和缓冲影响，不能保证精确帧，也不能直接替代原尺寸导出 |
| WebCodecs + mp4box.js / Mediabunny | 作为后续长视频候选，不作为本批首选 | 能在浏览器解码逐帧，但会引入新依赖、浏览器兼容、内存、整段媒体传输及鉴权适配；当前项目已有安全 FFmpeg 与精确 PNG 路径，先分层改造成本更小 |
| ffmpeg.wasm | 不采用 | 浏览器端包体与解码成本高，重复现有服务端能力，移动端压力更大 |

已读并用于选型的来源：

- [FFmpeg image2 muxer 文档源码](https://github.com/FFmpeg/FFmpeg/blob/master/doc/muxers.texi)：支持一次进程输出连续图片序列，适合批量预览准备。
- [WHATWG HTML 媒体规范](https://html.spec.whatwg.org/multipage/media.html)：浏览器能对已缓冲范围快速定位；未缓冲任意位置仍可能等待，不能把普通 seek 当成稳定逐帧合同。
- [W3C WebCodecs 视频解码示例](https://github.com/w3c/webcodecs/blob/main/samples/video-decode-display/index.html)：展示 mp4box.js 解复用后逐帧解码、画到 Canvas 的实现路径。
- [Mediabunny 源码仓库](https://github.com/Vanilagy/mediabunny)：提供 TypeScript/WebCodecs sample API，适合未来浏览器解码路线；当前未安装、未做兼容或包体验证。
- [mp4box.js 源码仓库](https://github.com/gpac/mp4box.js/)：BSD-3-Clause MP4 解复用实现，也是 W3C 示例采用的底层候选。

## 4. 确认后的页面与交互合同

### 4.1 全宽结构

1. `/multiview` 使用顶部导航壳层，不显示左侧导航；其他页面保持原样。
2. 工作台从两列改为单列全宽，拼图不再被右栏挤窄。
3. 拼图上方同一行放：`选帧`、`排版`、`查看原视频`；右侧空间足够时放 `3/4/8 张`、显示大小和撤销，窄屏自动换行但保持同一命令区。
4. 选帧、排版和原视频都在命令行下方以内联区域展开；一次只展开一个主工具，关闭后焦点回到原入口。
5. 删除底部重复“查看原视频”和右侧常驻页签；不删除其能力。

### 4.2 选帧操作

- 单张卡片下方原有左右键继续只调整该槽位当前帧；按住图片拖放继续只换拼图排列位置，两种操作不得串义。
- 展开的精确选帧区按以下顺序：

  `-10 帧` · `上一帧` · `指定帧输入框` · `跳到` · `下一帧` · `+10 帧`

- 下方增加全宽滑轨，范围为第 1 帧到最后一帧；显示“第 N / 总帧数 · 秒数”。拖动期间只更新轻量预览，不能每个 `input` 事件都请求服务端；松开或键盘确认后只预热目标附近分块。
- 指定帧输入使用 1 开始的用户口径；空值、非整数或越界在输入框旁就地说明并钳制／拒绝，不弹确认框。点“跳到”或按 Enter 执行。
- 键盘等价操作：左右方向键 ±1 帧，Shift+左右 ±10 帧，Home/End 到首尾；输入框聚焦时不抢普通输入键。
- “使用这一帧”和“取消”紧跟预览和帧控件，不放到远处。取消不改旧图；使用成功才替换槽位并进入撤销历史。
- “查看原视频”使用同一视频播放器，选帧预览与原视频播放位置可同步，但不自动播放声音、不在刷新后自动播放。

## 6. 接口与缓存约束

- 推荐新增只读授权端点：`GET /api/video/multiview/:id/previews?version=...` 返回版本化 manifest；预览分块 URL 只在相同授权和 `sourceVersion` 下读取。实现可按现有 App Router 再确定文件层级，但不得把低清预览混入现有精确帧响应。
- manifest schema v1 至少包含原片 `sourceVersion`、总帧数、每帧时间戳、单元尺寸、6×4 排列、每块首帧/真实帧数、MIME、字节数和 ETag；客户端遇协议或版本不匹配必须丢弃旧预览。
- 派生文件存入现有多视图临时缓存根的 `preview-v1/` 子目录，使用临时目录写入、完整数量/尺寸/MIME 校验后原子发布；任何 URL 都不得暴露服务器真实路径。API 保持 `private, no-store` 和 `Vary: Cookie`，每次 GET 重新鉴权。
- 单个图集的理论像素上限为 `24 × 320 × 320`；客户端最多同时保留当前块和一个相邻块的已解码图像，其他块只保留有界 Blob/元数据或按需重新读取。总帧数 ≤600 才可完整预取；超过后只准备目标块，不能为达成“秒切”伪装成全量后台占用。
- 预览准备复用现有总并发上限，但只允许一个低优先级预览 FFmpeg：仅在没有正在排队的精确帧工作时启动，且必须给精确应用/导出保留一个槽位。不能让预览抢占作品渲染或把 429 冒充完成；多 Web 进程场景实施前重核，若存在则补跨进程锁或停止上线。
- 单源准备须去重；失败保留原拼图和旧已选帧，显示“快速预览未就绪”，允许重试或使用现有精确帧慢路径，不重跑视频生成、不扣生成点数。
- `preview-v1` 按单源压缩体积 32MB、现有总缓存 1GB/24h/32 源的共同上限纳入清理；清理避开在写目录，只处理派生预览，不改变原尺寸帧配额语义。达到上限就停止新预览并保留旧拼图，不回落系统盘。
- 清理只处理派生预览缓存；不得删原视频、原尺寸帧、作品、账单、任务、历史或用户草稿。

### 7.2 性能完成标准

- 预览 manifest/当前分块已就绪后，连续上一帧／下一帧不再触发原尺寸提帧请求，点击到预览绘制 `p95 ≤ 100ms`（在项目既有 4 秒样例和一条真实标准 3D 短片上分别记录）。
- 首次无缓存允许有一次后台准备，但现有拼图必须继续可见；不得用纯阻塞页或假百分比冒充即时。

#### 真实状态与操作

| 情形及证据 | 主文案与必要补充 | 可用动作/边界 |
| --- | --- | --- |
| 点击生成，原请求发送中（可能仍在处理参考图） | 正在提交 | 生成按钮防连点；不宣称已受理或开始生成 |
| 仅本站已记任务，尚无上游受理证据 | 正在确认提交 | 原号核对；本地taskId不算供应商受理 |
| 已有可靠上游任务号且明确queued/pending/created | 已受理，等待生成 | 无队列名次、预计剩余时间或虚构百分比 |
| 上游明确running/processing/in_progress | 视频生成中 | 显示“提交后已用时”；local running兜底不作为开始证据 |
| 上游完成，原片还未可读/需下载探测 | 视频已生成，正在准备原片 | 必须在等待multiviewInfo之前切文案；不再显示仍在生成 |
| 原片可读，但尚未打开新结果、当前显示别的作品 | 新视频已就绪 | “打开新结果”；此时不能宣称图集/选帧就绪，不为通知偷偷打开和抽帧 |
| 已打开对应任务，图集/当前目标图片尚在加载解码 | 正在准备选帧；有实际数量时“已就绪3/8张” | 分母来自本次3/4/8目标；部分可用保留，慢图不能清空已可用图片 |
| 当前任务、同源版本的目标图片实际可用 | 可以选帧 | 可开始操作；已进入编辑后把状态收成安静完成文案，不持续庆祝或再次弹新结果 |
| 有原片、但快览失败且原尺寸读取可用 | 快速预览暂不可用，正在读取原帧 | 沿现有原帧回退；可编辑与快览性能分别表达，不一律判整个任务失败 |

上传有真实总字节时仍用原上传百分比；上传100%后尚未登记完成则显示“正在完成图片准备”。生成、原片下载和服务端图集构建当前无完整实时进度来源，首版只显示阶段。3/8等仅是当前选中目标图片的实际可用数，不是整部视频抽帧比例，也不证明原尺寸导出和作品云端保存完成。已有素材、已有视频、命中缓存直接跳过不适用阶段，不人为停留凑动画。

#### 异常、恢复与完成边界

1. **网络查询失败**：显示“状态更新暂不可用”，次行保留“上次确认：视频生成中”等真实最后状态；旧状态不继续冒充新确认。恢复成功撤提示；“更新状态”只查原任务、复用既有单一查询器，不额外开轮询或重发。自动查询预算用尽时明确“自动查询已暂停”，不无限活动指示。
2. **受理未知/上游状态不识别**：显示“提交结果待确认”或“生成状态待确认”，不能沿local running兜底说正在生成。保原号、原输入及冻结参数。“查询原请求”是主要恢复动作；原有显式“核对并结束本次提交”入口及服务端证明条件保留在现有恢复区域，不变成普通取消按钮。
3. **明确拒绝、失败或取消**：停止活动指示，显示安全且真实的原因，保主图/设置/旧作品。仅真实终态及既有合同允许时恢复“生成视频”入口；新点击仍是新请求和正常费用，不能把它标为免费重试。费用仅按实际账本状态说明，不从超时/失败文案推退款。
4. **视频成功、准备失败**：“视频已生成，原片准备未完成”或“选帧预览未准备好”，动作“继续准备”仅恢复本站读取/预览步骤，不重生成、不新扣生成费。失权时不重试受保护媒体、不展示旧敏感缓存，沿现有登录/权限恢复。
5. **有旧作品**：旧作品继续编辑，不被新进度替换或锁住；新结果就绪保留显式“打开新结果”，复用原切换和草稿保护。当前源码generationReady在部分相同sourceKey场景仍会自动切换，实施应对齐本设计：已有不同作品不自动切，真正无旧作品且用户未切换目标时沿原自动打开。主动换对象后迟到结果只提示，不抢回页面。
6. **刷新/重开/离开**：复用账号与Document隔离的receipt和现有恢复入口；只恢复请求身份，再查询真实状态，不保存loading为事实、不重发。成功受理后可离开，返回继续查询；上传、提交未知等保留原真实离开保护，不能统一承诺任意阶段都可关页。跨设备恢复不在本轮新增。
7. **计时**：有服务器created_at才显示“提交后已用时”，从同一任务时间计算，不称“已生成时长”；无可核时间就省略，不用恢复时刻补造。准备阶段继续标提交后总用时；完成后停在可核完成耗时，缺完成时间则只写完成。未识别状态/断网时不以计时增长暗示仍在执行。
8. **去重与优先级**：权限失效先处理；真实终态按上游及当前准备状态投影；查询异常是覆盖层而不是新业务终态。异步结果必须同时匹配账号、原key/taskId以及适用sourceVersion；旧/迟到响应不得覆盖新状态。相同任务已打开不再提示新结果；“打开新结果”在状态区仅保留一份，不与现有pendingResult通知重复。

详情只显示当前任务安全说明、真实发生的里程碑和必要失败原因。尚未观测到的中间阶段不打完成勾；无后台开始时间不编历史时间线。不上新全站通知、数据库事件系统、服务器推送连接或取消生成接口。

#### 落点、配套及实施验收

- GenerationPanel：扩展纯显示状态与onStateChange，不再把accepted一概缩成submitted；原片读取前立即切换状态。继承原receipt、防重、恢复与报价合同，上传单独保持真实回调。
- page：在设置折叠及editor隐藏区域之外渲染唯一状态区；将本次请求和当前作品分开，接pendingResult、previewState及实际目标图片解码数量，收口上述已有不同作品自动切换分支。保原保存/另存/播放/复制下载入口。
- status入口与序列化：只投影已获权限的受理/供应商状态/交付状态/已有时间；普通任务缺submission_unconfirmed时不能靠可选前端字段认定已覆盖，须根据真实受理证据生成显示投影。是否需加安全字段由届时最新代码差量决定；不改provider共享状态、finalizer、账务或路由。未知枚举映射为待确认。
- 不加新依赖，借鉴已读[Radix Progress源码](https://github.com/radix-ui/primitives/blob/main/packages/react/progress/src/progress.tsx)对未知value=null不输出aria-valuenow的语义；主状态用现有React/CSS和语义化状态文本即可。未安装、未声称项目已接入。
- 实施后统一覆盖：首次提交、仅本地任务/明确排队/真实运行/未知枚举、原片慢准备、图集未打开/3或4或8部分就绪、缓存跳阶段、有旧作品/打开新结果/重复通知、短断网/刷新/切号/迟到响应、失败后只恢复准备、快览回退、手机与减少动画。使用状态固定样本即可核分支；真实页面按项目由用户手验，不为每态付费生成。检查不会重复POST/费用/保存，不能仅以文案出现算闭环。
