# 产品、设计要求与展示合同

本文记录SD2已实现行为和用户已确认要求；实际客户端效果的验证边界见 [实现与证据](sd2-implementation.md)。

## 参与者和语义

| 角色 | 主要任务 | 权限 |
|---|---|---|
| 提交人 | 描述问题、附合法截图、知道是否保存 | 本人反馈、公开修复及本人回测，不看内部备注 |
| 指定接收人 | 飞书快速读意见、确认接收、打开详情 | 精确绑定账号，不是所有管理员都能代点 |
| 管理员 | 查看、备注、归档、明确修复并通知回测 | 原管理员权限，不能伪造提交人回测 |
| 投递器 | 独立准备图片和发送 | 固定应用、原接收绑定、受控原件 |
| 网关/本站 | 验签、授权、写接收事实、返回卡片反馈 | 来源验签不代替业务身份校验 |

接收确认、管理状态、修复轮次、投递状态、本人回测是并列维度，不能塞进一个“已完成”。

## 提交入口

网站复用浮动“提意见”入口：正文为主，截图可选；共享素材上传/粘贴和本人资产继续复用。现代插件复用同一服务器保存逻辑，带合法站点/插件版本，来源为 `/plugin/chatgpt`、`/plugin/midjourney` 或 `/plugin/jimeng`。

- 草稿按账号隔离；切号和迟到响应仍对应原账号，不清掉新账号或提交后的新编辑。
- 请求前保存原operationId、原内容和已上传附件；图片仍上传、失败或缺真实资产ID时就地处理。
- 服务器返回有效feedback.id后显示“意见已提交”；附件未通过核验时说明实际未保存数量。
- 清理本次已提交部分，保留后来编辑及新附件；全部空了才收起。成功提示在窗外短暂显示，不说“管理员已收到飞书”。
- 请求结果不明保原稿/原号；先GET原回执。明确not_found后可由用户沿原号重试，不自动造新号。
- 登录用户有“我的反馈”。网站兼容匿名文字反馈，不猜匿名用户的飞书账号；匿名反馈没有本人回测通知对象。

旧网站调用可以不传operationId，这是兼容路径，不能宣称所有旧客户端都具备现代提交去重。

## 新反馈飞书卡片

每条新反馈只给原批准的指定本人，不广播其他管理员、不自动催办、不汇总延迟、不补历史。后续给原提交人发回测是另一事件和接收规则。

现代图片准备分支实际顺序：

```text
┌ 新修改意见                         蓝色标题头 ┐
│ 脱敏的问题摘要（最多200字符）                   │
│ 合法截图1                                     │
│ 合法截图2……（有界，不裁掉关键区域）             │
│ 必要时：实际未附数量及原因                     │
│ 提交人 · 来源页面（较轻辅助信息）               │
│ Seedance2.0系统反馈通知                        │
│ [查看意见] 主按钮       [已收到] 次按钮         │
└──────────────────────────────────────────────┘
```

- 原卡用现有interactive 1.0风格：elements/div/note/action；不混Card 2.0字段或网页CSS。
- 用户正文用plain_text安全显示，不解析成Markdown、HTML、链接或群体提醒。摘要隐藏链接、邮箱、长标识；检测到password/token等敏感关键词时整段改为“内容可能包含敏感信息，请在后台查看。”
- 标题、正文、辅助信息有阅读层级，不全卡加粗、艳色或堆技术状态。消息时间交飞书客户端显示，不写固定“刚刚”。
- 图片经机器人接口上传，引用返回key；保实际比例，不为填框裁图、压缩或改原件。数量/大小上限是本站选择，不宣称平台无限支持。
- 无图不留空白图片区；有图但未附则说明真实原因，完整详情可达。正文脱敏没有扫描图片像素，不承诺截图中的秘密已消除。
- “查看意见”精确进入 `https://sd2.youdooart.com/admin/feedback?feedbackId=<id>`，登录和管理员权限继续生效。
- “已收到”是业务回调，不是跳链接。button.value仅带source、feedbackId、nonce、action，不带凭据或用户ID授权。
- 卡片冻结后不为重试换正文、按钮、接收人或格式；旧文字消息/无回执卡保持原样，不批量升级。

兼容的旧无图片准备分支顺序不同：系统来源note → 提交人/页面 → 摘要 → 截图数量 → 操作。不要用旧布局描述所有新卡。

## 点击“已收到”

成功返回success toast“已收到”，基于原冻结卡移除反馈确认按钮，尾部追加“已收到”；正文、图片和“查看意见”保留。更新原卡，不为确认另发一张。

- 原指定接收人才能确认。转发、错账号、失效绑定、错nonce不能改业务数据。
- 同一条重复点返回原receivedAt，不重记时间、不重复通知，不顺便改成reviewed/archived。
- 写入失败给错误toast，不先画成已收到。
- 写入成功而卡片解析/刷新失败，本站接收事实仍保留；不能撤销确认或再发通知。
- “原通知回执尚未确认”不是反馈不存在：必须和已保存原message_id对上，不绕过这项检查。
- 普通聊天手打“收到”、飞书已读、打开后台链接都不写receivedAt。

## 后台与本人详情

后台列表保“新反馈 / 已查看 / 已归档”、筛选、分页、导出与原权限。精确feedbackId可打开原详情，不因当前筛选隐藏它就误报不存在；失败保错误和恢复入口，不丢筛选现场。

详情阅读顺序：正文 → 提交人/时间/页面 → 截图 → 管理状态及内部备注 → “修复与回测”面板 → 按需展开的编号/URL/设备。截图缩略图contain并可放大，不能裁掉证据。

共同的 `FeedbackLifecyclePanel` 展示：

| 情况 | 当前文字/动作 |
|---|---|
| 无接收时间 | 尚未收到接收确认 |
| 有接收时间 | 已收到 · 相对时间 |
| 无修复轮次 | 尚无修复记录 |
| 有轮次 | 修复轮次选择、公开说明、发布时间和投递结果 |
| 等待作者 | 等待原提交人回测 |
| 作者已回测 | 本人回测通过 / 本人回测仍有问题，附说明和截图 |
| 管理员 | 公开修复说明 + 标记已修复并通知回测 |
| 原操作未知 | 原操作待核对，内容已保留；继续核对原操作 |

面板有手动“重新读取”，没有持续自动刷新receivedAt的承诺，旧面板可能需重新读取。正常展示简短事实，技术投递诊断不堆给提交人。

本人入口 `/feedback`、`/feedback/<id>`；列表只本人，每页24条。详情只返回本人原文/截图、接收事实、公开修复和本人回测，不返回admin_note、UA或他人资料。时间复用RelativeTime及其准确时间能力，不硬编码新日期口径。回测/修复草稿按账号、反馈、角色及轮次隔离，未知保原操作。

## 后续修复回测

这是已实现扩展，不是接收按钮的副作用：

1. 修复确实可供提交人使用后，管理员显式填公开说明并点“标记已修复并通知回测”。保存备注、已查看、归档、Git提交、部署都不自动触发。
2. 同事务存下一修复轮、operationId/输入hash、根revision及待发通知；恢复同一操作不重复建轮。用户主动用新operationId做新的修复动作会建下一轮，服务器不是按说明相同就自动永远去重。
3. 新卡标题“请回测反馈”，展示问题摘要/公开修复说明，按钮“打开并回测”到 `/feedback/<id>?round=<n>`，发给原提交人。
4. 原提交人选择“通过 / 仍有问题”，可补说明和合法截图，再“提交回测”。只本人、当前轮且未结论时生效；同号重放读原结果，旧轮不覆盖新轮。
5. needs_work把Feedback.status回new并清归档字段，保旧轮/通知。passed只存本人结论，不自动archived。

区分“回测通知待发送 / 已发送 / 通知结果待核对 / 未绑定飞书，可在本站回测 / 原反馈无提交账号，无法通知”等。发信失败不撤销修复，绑定变化不把旧事件改寄新账号。
