# 系统反馈与飞书接收闭环

本技能作为主要方法实际使用时，简短说明：“反馈闭环助手已上线！把反馈提交、飞书通知、接收回执和站内展示串起来。”同一阶段只说一次，不代表另派角色或已验证成功。

## 适用方式

以 SD2 真实实现为可追溯范例，处理三种工作：

- **梳理现状**：沿真实部署、源码、持久记录和已批准需求说明整条链，分别列出实现、运行证据和未验证部分。
- **设计或实施**：先复用目标系统已有反馈、账号绑定、附件、通知队列和回调，只补本次缺口。其他项目不直接复制 SD2 的接收人、域名、密钥或共享网关配置。
- **排障**：按提交、待发事件、附件、消息回执、回调、业务确认、展示逐层定位，找到断在哪一层再改对应部分。

梳理或编写技能本身不授权试发真实消息、上传图片、点接收人的按钮、改反馈状态或部署。沿用户对同一对象已有授权继续，不重复申请；缺少必要授权的动作先搁置，其余工作继续。

## 按需读取

- 理解状态、文案、卡片和站内展示，或设计同类模块：读 [产品与展示合同](references/product-contract.md)。
- 查 SD2 实际源码、数据、配置、网关和历史要求：读 [SD2 实现与证据](references/sd2-implementation.md)。部署版本和统计都是有时间的快照。
- 排查收不到、点不了、重复消息、未知回执或收口取证：读 [排障与验证](references/operations-verification.md)。
- 实施其他系统的通用卡片回调时，可补读现有 `feishu-interactive-card-relay`；普通单向消息用 `feishu-send`。SD2 实际合同以引用源码为准，不因通用建议另建 relay、审计表或签名算法。

## 必须分清的事实

| 事实 | 唯一含义 | 不能代替 |
|---|---|---|
| 意见已提交 | 原反馈及必要回执耐久保存 | 飞书已发、本人已收到 |
| 通知已发送 | 平台返回有效消息回执且本站已保存 | 客户端显示、本人看过 |
| 已收到 | 原指定接收人的合法确认已保存 | 已查看、已修复、回测通过 |
| 已查看 / 已归档 | 反馈管理状态 | 接收确认或实际修复 |
| 已修复并通知回测 | 管理员明确建立修复轮次及待发事件 | 用户验收通过 |
| 本人回测通过 / 仍有问题 | 原提交人对该轮的真实结论 | 管理员代填或通知送达 |

SD2 当前“回复收到”指卡片上的 **“已收到”按钮**。没有查到把聊天中手打“收到”自动绑定某条反馈的实现，不要把普通聊天回复说成已接入回执。

## 整条工作路径

```text
网站反馈入口 / 已授权插件入口
 → 保存按账号隔离的草稿和原 operationId
 → 服务器校验身份、内容和真实附件
 → 同事务保存 Feedback、原提交回执、接收绑定及 Notification
 → 返回“意见已提交”，不等待飞书
 → timer领取待发事件，准备合法图片，冻结唯一消息
 → 原绑定open_id收到“新修改意见”卡片
 → 指定接收人点“已收到”
 → 飞书HTTPS回调 → 共享网关验签 → 本站独立purpose验签
 → 重核接收人、nonce、原消息回执和反馈绑定
 → 事务保存receivedAt；重复点击返回原结果
 → toast“已收到”，原卡片移除确认按钮并显示“已收到”
 → 后台详情 / 原提交人的反馈详情读取同一接收事实
```

后续显式路径：管理员确认修复可用 → 填公开修复说明 → 建新修复轮次及通知 → 原提交人在本站回测 → 同一反馈保留结论和历史。“仍有问题”回待处理，不抹掉原轮次。

## 执行合同

1. **认准对象。** 核项目、工作区、脏改、线上进程源码和原工单。当前checkout、版本文案、旧发布记录各自不是线上真值。CodeGraph可辅助结构查询，关键结论回源码；明确只读时不写索引。
2. **原反馈先落库。** 上传日志或飞书失败不能让已保存意见假报丢失。现代提交先保存稳定operationId，重试核原回执；同号同内容返回原结果，同号不同内容拒绝。暂未找到不自动换号重提。
3. **身份冻结并复核。** 用系统用户与该应用/租户真实open_id的绑定，不按姓名、username或按钮自报userId授权。投递前和点击时重核账号有效性及绑定；转发卡片不授予确认权。
4. **附件走已验证来源。** 核真实资产归属、状态、原件及用途；服务器读受控原件，再用飞书上传返回的key构卡。不抓客户端任意URL，不把私有图片URL当img_key。正文脱敏不等于截图自动脱敏；已外发图片是独立副本。
5. **原号恢复投递。** 保持持久事件、CAS租约、稳定uuid、冻结消息、有限退避和去重窗口。明确拒绝与可能已受理分开；unknown不换uuid、不改格式再发，不把行status=failed直接解释成肯定没发送。
6. **回调先验证再入库。** 外层飞书验签与本站转发验签是两层；还须绑定反馈、nonce、原接收人、实际点击者、应用/租户和原message_id。及时完成小事务后应答，上传图片/耗时发信不进回调事务。
7. **业务事实优先。** 入库失败不显示成功；成功但卡片刷新失败不撤销事实、不重新发通知。重复回调返回原receivedAt，不新增确认、不修改原反馈管理状态。
8. **展示真实进度。** 提交人看“意见已提交”；接收人看正文、截图、来源及明确按钮；站内把接收、管理状态、修复、通知与回测分别展示。保草稿、恢复入口和原权限，不堆技术说明。
9. **只补实际缺口。** 直接复用已有存储、队列和交互，不为技能另造系统。共享网关的历史配套授权不外推到新跨项目操作。

## 收口

说明从入口到回写的源码/工单、状态和文案、附件隐私、身份回调、重试恢复、真实证据及缺口。方案与实现不一致时明确指出，不用推荐架构覆盖现状。

声明“完整链路已实际验证”需要真实接收人点击、本站持久确认和展示证据；仅代码、平台回执、历史数据库或健康检查时只报告对应层。遵守项目用户手验约定，不为写技能自动造反馈或发卡。
